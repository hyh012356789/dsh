# 002 授权

> 本文件译自英文原文 [002-authorization.md](../002-authorization.md)。如有出入，以英文原文为准。

授权决定谁能启动工作，以及这项工作可以包含什么。本文建立在 [001 领域模型](001-domain.md) 之上。

宿主负责执行允许列表、规则和授权。消息、评论和被引用的文档只是决策的输入；它们无法改变这些权限。

## 触发的两条路径

### 评估：决定是否启动工作

来源会记录一条消息是否指向智能体：`mention` 表示提及了机器人或智能体账号，`direct` 表示私信。准入环节检查发送者和该来源的策略：

- 允许列表上的人指向智能体时，构成明确请求。
- 人在带有工单的线程上跟进时，遵循下面的规则。
- 其余人类消息按其接收范围套用准入表。
- 来源机器人列表中的机器人可以产生推断候选，但绝不会产生明确请求。其他机器人不予准入。

### 订阅：延续已有工作

已订阅线程上的每条消息都会作为上下文到达其订阅的工单，包括来自机器人和 CI 的消息。这种投递绕过准入环节，也不授予任何新权限。每张工单仍受其授权限制。

工单自己线程上的人的消息，由该工单的执行器决定如何处理。主 Session 把消息附加到工单时也是如此。消息归执行器所有期间，它不经过评估，也不会得到决定。每个执行器要么在工单范围内处理该请求，要么把它交回，以便路由到别处。

只要工单仍在途，归属关系就持续存在，即使有人移除了它的订阅。对于并非被人停止、且有消息等待使其恢复的已结束工单，归属关系同样适用。

主 Session 会收到一条跟进通知。消息归执行器所有期间，主 Session 只能应人要求停止工作；接受、附加、忽略和重新排队都会被拒绝。停止仍需经过准入环节，使用下文所述的跟进强度。

### 交回与释放跟进消息

当一条消息请求超出工单范围的工作，或属于另一张工单时，执行器会将其交回一次。工单保留其订阅。如果被附加的线程与之无关，执行器会交回它在那个线程上拥有的消息。

只有当没有任何工单仍拥有一条消息时，它才会进入一次新的评估。其候选信息会包含各执行器给出的理由。准入环节按该线程上的普通消息来判定它，主 Session 可以接受它、把它附加到别处或忽略它。交回一张工单并不拥有的消息（例如机器人消息，或人已经送入评估的消息），不会排入任何队列。

工单结束时，会释放其执行器未读取或未接手的跟进消息。这包括从未投递给执行器的消息，以及在其最后一次报告或回合结束后才投递的消息，前提是执行器既未确认、也未答复或交回。每条被释放的消息在没有其他工单拥有它时进入评估。停止只结束被停止工单的工作。

被停止的工单不会再次把它的停止消息送入评估，除非另一张工单将其交回。执行停止的主 Session 可以把消息的其余部分作为新工作接受。

人可以从面板把一条已被拥有的跟进消息送入评估。如果主 Session 随后又把它附加回在途工单，执行器会再次收到它。当没有有效的判断覆盖该消息时，面板还会提供重新评估。

### 仅作上下文的订阅

执行器可以为获取上下文而关注相关线程，例如另一个 Issue 或 PR。其中的消息会到达工单，但不授予权限，也不带来跟进强度。那里的人类消息不会使已结束的工单恢复，除非主 Session 从该线程附加一条消息。主 Session 关于其他工作的说明同样只作上下文。

没有到达任何工单的人类消息（包括其工单已被人停止的线程）走评估路径。机器人消息无论是否投递给订阅的工单，都走这条路径。

## 强度

| 强度 | 情形 |
| --- | --- |
| explicit | 列表上的人指向智能体，或在已有工单的线程上跟进；准入表中设为明确请求的单元格 |
| inferred | 不在列表上的人在带有工单的线程上跟进，除非其准入表单元格为明确；准入表中设为推断候选的单元格；来源机器人列表中的机器人消息，且指向智能体，或到达来源接收所有消息的范围 |
| not admitted | 任何其他机器人的消息、准入表判定为忽略的一切，以及接受模式为 `off` 时的所有推断情形 |

对不在列表上的人，明确准入单元格即便在带工单的线程上也优先，并且在任何接受模式下都有效。否则其跟进属于推断，在 `off` 模式下不予准入。仅为上下文而关注的线程上的消息，使用准入表，而不是跟进强度。

## 准入

每个来源的策略都有一张准入表。它的行是接收范围：

- **飞书：**每个配置的群聊、机器人从中收到提及的其他群聊，以及私信。只有当飞书卡片上的 **其他群** 设为 **仅 @** 时，才会接收其他群聊。
- **GitHub：**新 Issue、新 PR、评论和默认分支的 CI。

一行最多有三个单元格。每个单元格决定消息成为明确请求、推断候选，还是什么都不是：

| 单元格 | 选项 | 默认 |
| --- | --- | --- |
| 在列表上，未指向智能体 | inferred, ignore | inferred |
| 不在列表上，指向智能体 | explicit, inferred, ignore | ignore |
| 不在列表上，未指向智能体 | inferred, ignore | ignore |

针对“未指向智能体”消息的单元格，只在来源接收所有消息的地方可用，例如设为 **全部消息** 的飞书群聊，或开启了接收全部开关的 GitHub 范围。CI 结果没有发送者，因此其行只提供最后一个单元格。机器人消息使用机器人列表，而不用这些单元格。

把“不在列表上、指向智能体”这一单元格设为 explicit，可以让该范围内的任何人通过提及智能体来请求工作。这对专门的支持群聊可能有用。推断候选仍取决于接受模式。跟进通常绕过此表，但 explicit 单元格仍会赋予明确强度。

准入表是策略版本的一部分。削弱某个单元格的准入不会立刻停止在其下已被接受的、已开启的工单。但当这些工单在恢复前被重新校验时，可能会撤销其授权。

### 机器人与自动审查者

宿主把 GitHub App、以 `[bot]` 结尾的登录名以及飞书机器人识别为机器人。来源可以列出诸如 `dependabot[bot]` 的机器人，它们的消息可以成为推断候选。它们必须指向智能体，或发布在接收所有消息的范围内。它们不能发起明确请求，也不能停止工单。

使用普通账号的自动审查者，在宿主看来算作人。其评论会到达订阅的工单，并产生跟进通知。团队提示词文本必须把这类账号标记为自动审查者。

## 路由候选

主 Session 用 `orchestrator_route` 路由明确候选。一次调用可以包含多个接受、附加、停止或忽略决定。每一项都独立处理：某一项被拒绝或缺少字段，不会妨碍其他项执行。

推断候选通常需要完整的研判。有一个捷径：如果其卡片明显不涉及任何已启用的规则，例如普通聊天或无关讨论，主 Session 可以直接忽略它。决定会记录 `ignoredFromCard`，以区别于按规则作出的研判。主 Session 在其策略提示词部分读取已启用的规则。

接受推断候选始终需要研判。直接接受会拒绝准入环节未以明确强度准入的触发。

## 接受模式与规则

接受模式是策略的一部分：

| 模式 | 效果 |
| --- | --- |
| `off` | 任何推断内容都不会成为候选，例如未指向智能体的消息、机器人消息，或不在列表上的人的跟进 |
| `observe`（默认） | 推断候选会被研判；肯定的研判会记录为带“本会接受”标记的忽略，不会接受任何工作 |
| `auto` | 对推断候选的肯定研判会接受它 |

明确请求在任何模式下都有效。从 `observe` 开始，审查过记录的决定后再切到 `auto`。每次研判都会对每条已启用的规则判断恰好一次，无论是否匹配。主动接受要求至少匹配一条规则。

每条规则描述一类主动工作。工单的授权会记录匹配到的规则，其执行器会收到这些规则的名称和说明。

对该工单而言，规则中的流程和沟通要求会覆盖默认值。沉默规则可以抑制确认回复；审查规则可以指定合并前所需的审查者和批准。适用于所有工单的要求则应放在团队提示词部分。

## 策略版本

规则、接受模式和每个来源的策略共同构成策略版本。每个授权都会记录它被接受时所依据的版本。

版本变更会丢弃正在运行的评估，并重新排队它们的触发。它还会向每张受影响的在途工单发送一条“策略变更”输入。该输入会说明是以下哪种情况：

- 匹配的规则发生了变更（包括其新文本），或已不再适用；
- 请求者已不能再启动工作；或
- 主动工作不再被接受，例如因为模式已从 `auto` 改变。

未受影响的工单不会收到通知。变更不会立刻撤销在途工单的授权。

来源配置与策略相互独立。它控制系统接收什么：读取哪些群聊，以及某个范围是接收所有消息还是只接收提及。授权会记录其来源和接收范围。恢复要求来源仍在监听该线程，但不要求它仍在该线程接收所有消息。

来源关闭时，回复会等待。如果来源不再监听其目的地，回复会被丢弃。

对执行器可以如何处理自身结果的约束（例如何时可以合并）不决定谁能授权工作。它属于智能体的指令，而不属于策略。

## 恢复与停止

已结束的工单保留其授权。有人在其某个自有线程上发消息，就能恢复同一项工作，无需新的评估或决定，也不论发送者是谁。机器人和 CI 不会唤醒已结束的工单。由执行器判断请求是否符合范围；若不符合，则结束本轮。

只有三种操作会改变授权：接受会创建它，人的停止会撤回它，重新校验失败会撤销它。被人停止的工单保持结束状态，不再接收任何内容。若要在那里请求工作，需要新的接受。

### 恢复前的重新校验

来源必须仍在监听原始线程。其余检查取决于授权的依据：

- 明确跟进的授权直接通过。
- 推断的授权需要 `auto` 模式，且其匹配的规则仍然启用。
- 由表格单元格准入的授权，在今天的表格和发送者成员关系下仍须至少获得其原有强度。因此，把发送者移出列表可能会撤销通过“在列表上的发送者”单元格接受的授权。
- 机器人的授权要求该机器人仍在来源的机器人列表上。来自推断表格和机器人的授权还需要 `auto` 模式以及匹配规则仍启用。
- 其他授权要求发送者仍在来源的允许列表上。

若重新校验失败，工单保持结束，且不接收任何等待中的消息。每条消息都视为未到达任何工单；如果没有其他工单拥有它，它就进入评估。主 Session 不会被告知它到达了某个工作者。处理暂停之后同样如此。向该工单附加会被拒绝，进一步的工作需要新的接受。

- **人在线程中说“停止”只是一个普通触发，** 由评估决定是否停止。执行器不能宣称有人要求它停止。
- **面板中的停止是一条命令。** 它直接作用于工单，并被记录为手动停止。
- **等待类条件属于来源。** 像“N 小时无人负责”这样的条件，会由一个自行等待并再次检查的来源来实现；评估从不等待。

## 评估未完成时

时限从候选到达主 Session 时开始计时。等待投递的时间不计入，未投递的候选永远不会过期。

超时的评估会重新排队其触发，以便再试一次。连续两次重试之后，第三次超时会记录 `unavailable`。研判失败同样记录 `unavailable`；之后的触发可以启动新的评估。策略变更，或基于过时策略做出的决定，会记录 `unavailable`，并立即按当前版本重新排队该批次。

`evals` 健康条目会报告最近一小时内未解决的 `unavailable` 决定。`scripts/dsh-superagent status` 会包含这个错误。

只有在 `unavailable` 决定不满 24 小时、仍是其线程上最新的决定、未被忽略，且该线程既未排队也不在评估时，面板才会请求人工介入。人可以重新评估该触发，或忽略这个问题。
