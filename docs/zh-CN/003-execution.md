# 003 执行

> 本文件译自英文原文 [003-execution.md](../003-execution.md)。如有出入，以英文原文为准。

本文跟踪一个已被接受的工单，走完执行、交付与恢复的全过程。它建立在 [001 领域模型](001-domain.md) 和 [002 授权](002-authorization.md) 之上。

## 工单阶段

每个未结束的工单都只有一个阶段，由它正在等待什么决定。请从上到下阅读下表，第一行匹配的就是它的阶段。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| person / delivery | 向执行器 Session 投递输入失败；会在 2 秒后重试，之后的重试间隔逐次翻倍，最长到一分钟；一旦投递成功、出现新的派工或工单结束，该状态即被清除 | 输入未送达 |
| person / answer | 存在待人工决定的事项 | 等待答复 |
| person / review | 最新的报告为 `ready` | 等待审查 |
| person / blocked, failed | 最新的报告为 `blocked` 或 `failed`，且此后没有人的消息到达该工单 | 受阻 · 失败 |
| working / queued | 没有派工，或派工尚未启动 | 排队中 |
| idle | 最新的报告为 `waiting`，或派工已结束 | 等待触发 |
| working | 其他所有情况 | 工作中 |

`person` 阶段意味着工单没有人工输入就无法继续。一条新的人类消息会把 `blocked` 或 `failed` 的工单释放给它的执行器，于是工单转入下一个匹配的阶段，通常是 `working`。

处于 `idle` 的工单已经结束本轮，且没有悬而未决的问题。已订阅线程上的一次触发可以让它继续。

## 执行器

每个工单都会获得一个名为 `worker-<ticket id>` 的执行器 Session，以及一个以工单短名命名的目录。目录创建在配置的执行根目录下，默认是 `<stateDir>/work`。

执行器 Session 以运营者的操作系统用户身份运行命令，无需审批。它们的 `dsh-superagent-worker` 预设包含完成工作所需的工具，并会在 5 秒后把前台 shell 命令转入后台任务。这样工作者在下一步就能收到新消息，而不必等一条长命令跑完。

主 Session 使用 `dsh-superagent-router`，具有相同的 5 秒 shell 和任务等待上限，以及一套更小的、用于路由的工具集。会话会保留创建时选定的预设。工作者的子智能体使用 DeepSeek Harness 的 `standard` 预设。

### 后台工作与工作者槽位

如果一轮结束时仍有 shell 任务或子智能体在运行，工单会保留它的工作者槽位并保持工作状态。它不会被报告为等待中，主 Session 也不会收到等待报告。任务或子智能体完成后，会在同一槽位中用其结果唤醒执行器。一旦某一轮结束时已没有后台工作，执行器就会照常报告等待。

每轮结束后，后台工作最多有 30 分钟用于完成。到达该上限时，shell 任务会被终止，工单报告为等待中。报告包含执行器最后说的话，以及哪些任务被终止、哪些子智能体仍在活动。子智能体允许继续运行。执行器会在下一轮读取被终止任务的结果。

向人交接会立即释放槽位，并让报告继续生效。这适用于 `ready` 报告或提问之后（除非此后又到达了其他输入），也适用于任何 `blocked` 或 `failed` 报告之后。

交接时，子智能体停止。shell 任务（例如为审查而提供的一台服务器）可以继续运行，直到派工结束。它们不占用槽位，也不受 30 分钟上限的约束，后续轮次结束后同样如此。它们完成时不会唤醒执行器；执行器会在下一轮读取结果。

人也可以直接在执行器 Session 中写入内容，从而开启一轮。其后台工作遵循同样的规则。

派工结束时，它的 shell 任务会被终止，且不会唤醒会话。它的子智能体被释放，由它们唤醒的任何完成轮次都会被丢弃。替代的派工及其等待中的输入会在该关闭过程结束后才开始。

在 DeepSeek Harness 进程内停止或重启插件，走的是同一条关闭路径。尚未进入会话历史的输入会被保留。关闭过程最多为每个工作者的后台工作等待 10 秒；进程重启则会直接终止这些工作。忙碌中被中断的派工在重启时会带一条恢复说明。

工作者的子智能体（包括嵌套的子智能体）使用 DeepSeek Harness 的 `standard` 预设，并沿用工作者的权限。它们只保留工作者被允许的工作工具，并在工单结束时失去这些工具。在 `standard` 下，shell 命令在 60 秒后转入后台。子智能体结束时，它的任务会被终止。

### 准备工单目录

在第一次派工之前，如果工单目录不存在，准备命令会在执行根目录中用 `sh` 运行一次。它有十分钟时间完成。没有准备命令时，工作者会在一个空目录中启动。

命令失败会使工单失败，并记录其输出。重试，或者人在该工单的某个线程上发消息，都会再次尝试准备。典型的命令用 `git worktree` 创建一个检出。当 PR 分支名的最后一段与该工单的短名一致时，这个 PR 就属于该工单。

### 并发

工单从一次启动开始（含准备阶段）就占用一个工作者槽位，或者从唤醒其空闲执行器的那次投递开始占用。在整个活动轮次期间，它也一直占用该槽位。

配置的并发上限适用于这些槽位，另有一个额外槽位供人的消息或状态查询使用。当普通槽位已满时，这类唤醒可以使用额外槽位；而在新的启动之前，它会先占用下一个空闲槽位。因此新工作无法阻止人继续推进一个已有的工单。

其他输入（例如 CI 结果）要等待普通槽位。一次启动会在 `working / queued` 中等待，直到有槽位空出。启动是并发进行的，所以一条缓慢的准备命令只会拖延它自己的工单。

### 执行变量

准备命令和执行器指令收到的是同一批执行变量。命令读取环境变量；执行器在其提示词中读取这些变量的值和描述。它们都不含凭据。

| 变量 | 注册方 | 值 |
| --- | --- | --- |
| `DSH_SUPERAGENT_DIR`、`DSH_SUPERAGENT_NAME`、`DSH_SUPERAGENT_TICKET` | 执行器 | 工单的目录、短名和 id |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | 执行器 | 执行器不得运行的命令 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | 来源所监听的仓库，`owner/name` |
| `DSH_SUPERAGENT_GITHUB_ACCOUNT`、`DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | 智能体账号及其提交邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER`、`DSH_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 发起该工单的 Issue 或 PR；若为 PR，还有它的 head ref |
| `DSH_SUPERAGENT_FEISHU_BOT`、`DSH_SUPERAGENT_FEISHU_CHAT` | 飞书 | 机器人，以及发起该工单的群聊 |

工单专属的值来自它的目录和发起它的触发。其他值来自当前的部署设置。只有面板能修改执行环境的设置；发送给主 Session 的文本无法改变已配置的 shell 命令。

工作者通过智能体账号的 `gh` 访问 GitHub，通过机器人的 `lark-cli` 访问飞书。被禁止的命令在按名称调用时会失败。

这些包装器和目录只确立默认值，并不构成安全边界。工作者仍然可以通过绝对路径执行程序。

## 合并

自动合并由 **交付要求** 提示词管辖。宿主没有任何专门针对合并的决策逻辑。

默认情况下，执行器绝不以智能体账号的身份启用自动合并：GitHub 会把这次合并归到启用它的人名下。交付要求必须指定另一个账号的 CLI 来完成合并。若没有指定，就由人来合并 PR。

默认指令只允许对为该工单创建的 PR 启用自动合并，前提是它已就绪、所需的批准覆盖了 head 提交，且新增与删除的行数合计少于 200 行。在推送另一个修订之前，执行器会撤回自动合并。

没有正文的审查（例如批准）也会作为触发到达，并能唤醒正在等待审查的执行器。这些指令约束的是智能体，而不是 GitHub 的合并规则。要强制批准，请在分支保护中要求批准并撤销过期的批准。省略合并 CLI，或删掉自动合并那一段，即可要求人工合并。

## 工单如何结束

- **就绪但没有 PR：** 一份 `ready` 报告以“已完成”结束该工单。
- **无事可做：** 执行器若发现没有需要人处理的工作（例如请求无法复现或已被取代），会报告 `dropped`。工单会在不发消息的情况下结束，除非有匹配的规则要求发一条；人此后在其线程上发消息可以恢复它。

### PR

一旦执行器报告了它最初的来源 PR，工单就会跟踪该 PR。它还会跟踪从其分支创建、并由执行器报告或由 GitHub 来源发现的每一个 PR。被重新打开的 PR 会再次被跟踪。

当工单创建的 PR 都不再处于打开状态时，工单即完成。如果它没有创建任何 PR，则它跟踪的所有 PR 都必须已关闭。随后它带着最后一次相关关闭的结果结束，并保留其订阅，从而允许此后的人类评论恢复它。

只要被恢复、被重试或从重启中恢复的工作尚未完成，关闭就不会结束工单。如果执行器已确认或答复了由它负责的后续消息，但此后尚未做出一份表明没有进展的报告、也没有在读到该消息后结束一轮，关闭同样会等待。之后一旦满足同样的 PR 完成规则，随后的 `ready` 报告就会结束该工单。

聊天渠道会收到一条关于 PR 结果的最终通知。GitHub 本身已在 PR 上展示这一结果。移除工单对某个 PR 的订阅，也会让它停止跟踪该 PR。

因此，“等待审查”意味着带有一个 PR 的 `ready` 报告。

### 后续消息与上下文线程

执行器就其工单自身线程上的人类后续消息作出决定。它处理范围内的请求，并把超出其范围或属于其他工单的请求交回。一旦没有任何执行器认领该消息，它就成了主 Session 的候选。除此之外，主 Session 只能应人的要求、为停止工作而对该后续消息采取行动。

输入在被会话纳入某个步骤，并在随后做出报告或结束本轮之后，才算已读。工单结束时，未被确认、答复或交回的未读消息会回到评估，如 [002 授权](002-authorization.md) 所述。已读但没有被处理的消息（例如感谢）则不会。

仅为上下文而跟踪的线程仍会投递消息，但不会让工单拥有人类后续消息的归属，也不会恢复已结束的工单。这些消息可以被独立研判。

只要有活跃的工单在订阅，来源就会轮询已订阅的线程；并且在最后一次触发与订阅方工单结束这两者中较晚的那个时点之后，还会再持续两周。此后，消息只能通过常规入口到达：GitHub 通知或飞书实时事件。

## 故障与恢复

### 执行器受阻或失败

当执行器 Session 报告 `blocked` 或 `failed`，或启动失败、出错（记为 `failed`）时，工单不再接收自动输入。

模型提供方或网络的暂时性故障（HTTP 408、429 或 5xx，或连接被拒绝、被重置、超时）会先重试三次，退避时间逐次增长：一次启动会重新执行，一轮失败的工作者会被要求继续；失败的准备命令则不会重试。

一旦失败，CI 和机器人消息会记录在该工单上，但不会被投递，也不会唤醒会话。

它的工具仍然可用，所以人可以直接在该会话里继续。

失败的启动不会自行重试。

人的一条消息、此后一份既不是 `blocked` 也不是 `failed` 的报告，或一次重试，都会解除这一挂起状态。

该状态由已存储的报告和输入推导得出，因此重启后依然保持。

### 重试

当未结束的工单处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可用：对每一种情况，补救办法都是启动一次新的派工，它会重新启动工作者并接收等待中的输入。

一旦人的消息到达了受阻或失败的工单，执行器就拿到了该消息，因此工单显示为工作中，或者在失败的启动重新开始时显示为排队中，并且不再提供重试，除非投递那条消息本身失败了。

重试会结束当前的派工，并在同一个执行器 Session、目录、分支和 PR 中启动新的派工。

执行器模型只在创建会话时生效；已有的会话保留它原来的模型。

### 重启

正在运行的派工以 "host restarted" 结束，新的派工则以一条恢复说明开始，该说明要求执行器在重复任何外部操作之前先检查自己的目录、git 历史和 GitHub；处理顺序是最旧的工单优先。

处于等待、就绪、受阻或失败状态的派工保持原样，除非在那份报告之后有输入到达，这种情况下它们也会重新启动。

会话、目录、订阅、待处理消息以及下文所述的已存储工作都能在重启后保留；同样保留的还有每个执行器 Session 把哪些消息纳入了历史的记录——步骤在认领消息之后、调用模型之前完成这一动作：被重启截断的一轮取走的消息，只要随后有一份报告或一轮结束，就算已读；而某个步骤已认领、却在进入历史之前被取消或出错截断的消息，则算未读。

重试或重启会把被替代的那次派工收到、但其执行器 Session 没有取走的消息（可能因取消或被截断的步骤而丢失）重新交给新的派工；仍留在会话中等待的副本（由重启保留，或跨崩溃持久化）会在新派工的第一条消息之前被取出，因此新的投递是唯一的副本。

### 已存储的工作

dsh-superagent 在做出决定之后要做的事，例如把候选、后续消息或报告转发给主 Session、启动派工或投递输入，都是先存储、后执行。

失败的中转或投递（例如无法触达其会话）会在 2 秒后重试，之后延迟逐次翻倍直至一分钟；启动失败会使它的工单失败，除非该失败属于上文所说的暂时性故障。

每一类工作只有在某一项连续失败三次之后，才会在概览的系统问题中报告错误；输入投递失败则改为显示在它的工单上。

发往主 Session 的中转保持先后顺序，通知也是如此；失败的一项会挡住同类中更晚的项。

### 来源故障

GitHub 来源分别读取每个 Issue、PR 和线程：一次读取失败会把错误留在它的线程上，在下一次轮询时再读，并计入来源的错误数；默认情况下，来源会在一连三次轮询失败后报告该错误；任何一次成功轮询都会重置计数。

当智能体失去对私有仓库的访问权限时，GitHub 也会返回 404，因此 404 会被重试。

被通知的 Issue 或 PR 若读取持续失败，会在首次读取失败一天后被丢弃；若 GitHub 报告它已被删除，则立即丢弃。此后它不再导致轮询失败，它的线程保留该错误，来源的状态中会点名它。

它的读取位置留在原处，因此之后的通知或对其线程的轮询会读到失败期间遗漏的内容。

飞书事件消费者会报告每一次失败；对已订阅主题的轮询会把每次失败留在对应的线程上。

GitHub 列表或飞书页面中格式错误的项会被跳过，来源的状态会将其计入。

### 渠道故障

外发消息作为已存储的工作被保存并发送，重试采用从 5 秒起、逐次翻倍直至 300 的退避。

工单发往同一个对话的消息按入队顺序发出，因此它的确认会先于之后的答复或结果：当同一工单发往同一对话的更早一条消息尚未发出时，这条消息会等待，直到那条消息连续失败三次并显示为问题。

其他工单的消息，以及不属于任何工单的消息，都不会等它。

有失败尝试的消息在发出或被撤回之前，都算作系统问题。

只有当它的来源不再监听该对话，或者来源回复说该对话永远无法接收它时，消息才会被丢弃；当它的来源关闭时，消息会等待。

对于 GitHub 上已删除的 Issue 或已锁定的对话，以及已被撤回的消息或飞书已经找不到的消息，来源会给出这样的回复。

对已不存在的审查评论的回复，会改为发到该 PR 的对话中。

被丢弃的消息会保留记录，其中包括丢弃的时间和原因，以及它原本属于哪个工单，因此它绝不会再次入队；被丢弃的确认显示为已丢弃，而不是已发送。

### 暂停处理

停止调度、新的评估、评估超时、输入投递和回复；已经在进行的启动会等到处理恢复。

来源会继续记录触发，正在运行的执行器轮次不会被打断。

发给已结束工单的人的消息会等待：暂停后的第一轮处理会恢复该工单，前提是它的授权在当时的策略下依然成立。

进行中的评估不会在暂停期间过期；它的截止时间会按暂停的时长向后顺延。

### 无效配置

某个已存储的来源配置若被其类型拒绝，则禁用该来源实例。
